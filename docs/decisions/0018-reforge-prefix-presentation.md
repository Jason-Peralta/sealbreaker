# 0018 — The reforge prefix is one component; presentation derives from it through a GearItem base class
Date: 2026-09-05
Status: accepted
Context: a reforged item must show its prefix in the name, in a tooltip line and as a visual mark. Spike S4 weighed deriving all three from the `sb_core:reforge_prefix` component at display time (needs our own item class, since vanilla's name comes from `Item.getName`) against writing extra vanilla components (`item_name`, `enchantment_glint_override`) whenever the prefix changes (works on any item, but two or three components to keep in sync and names baked into saves).
Decision: the component is the single source of truth. Every reforgeable item extends `dev.sealbreaker.core.api.item.GearItem`, which composes the name (`reforge.sb_core.named`, prefix first, from lang keys) and answers `isFoil` from the component; the tooltip line comes from the component itself (`TooltipProvider`) placed through NeoForge's `RegisterTooltipAppendersEvent`; item model definitions may react to the component with `has_component`/`component` conditions. Loot tables and the reforge transaction write only `sb_core:reforge_prefix`.
Consequences: weapons, armor and accessories are `GearItem`s (or subclasses), never plain `Item`s; a vanilla item cannot carry a visible prefix, which is fine because none is reforgeable (decision 0006); lang changes and resource reloads never leave stale names in saves; renaming a modifier id is a data migration like any registry rename. Other component-driven lines (rarity, armor set bonus) follow the same appender pattern.
