# 0019 — Realms are datapack dimensions on their own 26.2 world clock, entered through Portal blocks
Date: 2026-09-05
Status: accepted
Context: the realm plan assumed a custom dimension with its own daylight cycle and our own gate block. Spike S3 showed that 26.2 provides the cycle as data (a `world_clock` entry, a `timeline` on that clock with the day length, markers and visual tracks, and a `dimension_type` naming both) and that the vanilla `Portal` interface carries a block-based gate end to end, including a second connected player watching. The alternatives were a hand-written clock and sky renderer, or a teleport command in disguise.
Decision: every realm is five data files (world clock, timeline, timeline tag, dimension type, level stem) plus biomes; its gates are blocks implementing the vanilla `Portal` interface whose `getPortalDestination` reads the `sb:realm` registry (target, transition time, Seal, return rule) and refuses entry by returning null when the Seal is not broken; return travel is never gated. Realm clock speed is a data value applied through `ServerClockManager.setRate` on world load.
Consequences: no custom time or sky code; realm tuning happens in JSON and reloads with the world; a Seal gate is one server-side check in one method; the game test server cannot host datapack dimensions, so portal trips are verified with the two-client LAN harness while data and gate refusal are game-tested; a vanilla client on our server would desync on non-default clock rates (irrelevant: the pack is required on both sides).
